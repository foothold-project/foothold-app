## 1. 개요

### 1.1 제품 한 줄 정의
조직이 가진 사족보행 로봇 여러 대를 **한 화면에서 관제하고, 직접 조종하고, 임무 시나리오로 자동 실행시키고, 그 결과를 기록**하는 웹(PC)·모바일 운영 플랫폼.

### 1.2 최종 목표
실제 현장에서 로봇을 제어하고 임무 명령·진행·결과를 관리하는 앱. 조종·지도·인증 연결은 중간 기반이며 개발 종료 조건이 아니다. (확정, 10-06)

### 1.3 범위 경계
- 첫 대상 로봇은 Unitree Go2. 다른 로봇 호환은 향후 계획으로 구조만 열어 둔다. (확정)
- 적용 분야·첫 임무·작업 장비는 미정. 소방은 예시일 뿐이다. (확정)
- 장비나 로봇이 지원하지 않는 작업을 실행 가능하다고 표시하지 않는다. (확정)
- 배터리·부착 장치 정보는 실기 Go2 에서 받을 수 있다. (확정, 10-19 제품 책임자 확인. 토픽 이름·필드는 [04 §6](04-ARCHITECTURE.md) 에서 실기로 확인할 항목)

### 1.4 지금 앱과의 차이 (요약)
| 구분 | 지금 앱 (2026-10-19, 98242c7) | 이 PRD |
|---|---|---|
| 로봇 수 | 실제 연결 1대, 바꾸려면 새로 고침 | 여러 대 동시 관제, 화면에서 바로 선택 |
| 역할 | 역할 개념 없음 | 총괄 운영 관리자 / 운영 관리자 |
| 결재 | 없음 | 결재 탭에서 지도·시나리오 배정·긴급 실행 처리 |
| 임무 | 사람이 몰고 버튼은 기록만(수동) | 시나리오 자동 실행(Nav2), 다른 층까지 이동 |
| 화면 | PC 메뉴 7 + 숨은 화면 6, 폰 탭 두 벌 | PC 6탭(+설정), 폰 3탭 |
| 뎁스·배터리 | 없음 / 미제공 | 표시 |

## 2. 사용자와 역할

### 2.1 역할 정의 (확정)
| 역할 | 코드 | 담당 범위 | 접속 기기 |
|---|---|---|---|
| 총괄 운영 관리자 | `ORG_ADMIN` | 조직의 모든 로봇·계정·지도·임무. 결재권자 | PC (폰은 결재·알림 확인용, 제안) |
| 운영 관리자 | `OPERATOR` | 자기에게 등록된 로봇 1대 이상 | PC, 폰 |

- 한 조직에 총괄 운영 관리자는 1명 이상 둘 수 있다. (제안: 결재권자 부재 대비)
- 운영 관리자는 다른 사람의 로봇을 **볼 수는 있지만 조종·배정할 수 없다**. (확정: "조종할 수 있는 로봇만 내가 등록한 로봇으로 한정")
- 보기 전용 계정(`VIEWER`)은 이번 범위에서 만들지 않는다. 필요하면 역할 표에 한 줄 추가로 넣을 수 있게 설계한다. (제안)

### 2.2 대표 사용 장면
1. **총괄, 아침 점검**: 관제 탭에서 전체 로봇 수, 임무 중인 로봇, 주의가 필요한 로봇(연결 끊김·배터리 부족·오류), 결재 대기 건수를 본다. 결재 탭에서 밤사이 들어온 지도 수정 요청 2건을 승인한다.
2. **운영 관리자, PC 에서 임무 준비**: 임무 탭에서 "2층 계기판 점검" 시나리오를 만들고 자기 로봇 Go2-3 에 배정을 요청한다. 총괄이 승인하면 배정이 확정된다.
3. **운영 관리자, 현장에서 폰으로 실행**: 폰 시나리오 탭에서 카드 하나를 누르고 확인하면, 1층에 있던 로봇이 2층 시작 지점까지 스스로 가서 시나리오를 실행한다.
4. **조종권 요청**: 운영 관리자 A 가 Go2-3 을 조종 중일 때 총괄이 조종을 요청하면, A 의 화면에 "총괄 김OO 님이 조종권을 요청했습니다. 넘겨주시겠습니까?" 가 뜨고 A 가 고른다.
5. **긴급 실행**: 결재권자가 응답하지 않는 상황에서 운영 관리자가 이유를 적고 시나리오를 즉시 실행한다. 총괄에게 즉시 알림이 가고, 결재 탭에 사후 확인 항목이 남는다.

## 3. 문제 정의
1. 지금 앱은 로봇 1대 기준이라 조직 단위 관제를 할 수 없다.
2. 임무가 "사람이 직접 몰고 버튼으로 기록"하는 수동 방식이라, 시나리오를 눌러 실행시키는 기획 흐름을 받칠 수 없다.
3. 화면에 개발·검증용 문구(관문·링크·명령 0·HTTP 404 등)가 섞여 있고, 같은 기능이 여러 화면에 흩어져 있어 주요 작업에 5~10번 누른다.
4. 역할·결재가 없어 "누가 무엇을 바꿨고 누가 허락했는지" 남지 않는다.

## 4. 목표와 비목표

### 4.1 목표
- G1. 총괄이 조직의 모든 로봇 상태를 **한 화면, 한 번 누름**으로 파악한다.
- G2. 운영 관리자가 자기 로봇의 조종권을 **3번 누름 이내**로 받고, 잠금 해제까지 4번 안에 움직일 수 있다([03 §6](03-UX-SPEC.md#6-누름-수-예산-인수-기준)).
- G3. 폰에서 시나리오를 **2번 누름**(카드 → 확인)으로 실행한다.
- G4. 지도 수정·시나리오 배정·긴급 실행이 **결재 탭 한 곳**에서 처리되고 모두 기록된다.
- G5. 기존 안전 규칙(STOP, deadman, 조종권 1인, 재접속 시 잠금)을 하나도 약화하지 않는다.

### 4.2 비목표 (이번 범위 아님)
- 로봇 사이 교통 관리(같은 복도 양보·우선순위). 경고만 한다. ([04 §5.4](04-ARCHITECTURE.md))
- 충전 도크 자동 귀환 (Go2 기본 구성에 도크가 없음. 미확인)
- 엘리베이터 연동 (층 이동은 계단 기준. 엘리베이터는 향후)
- 로봇 여러 대 동시 조종(한 사람이 두 대를 한 번에 모는 것)
- 일정 반복 실행(매일 9시 등). P2 후보
- 가스·LEL·음성·AI 탐지 등 미연결 장비 화면

### 5.5 임무·시나리오 (MS)

| ID | 요구사항 | 우선 |
|---|---|---|

## 8. 가정·제약·위험
| 구분 | 내용 | 대응 |
|---|---|---|
| 위험 | Nav2 자율 이동이 시뮬·실기 Go2 에서 안정적으로 될지 미확인 | R0' 에서 먼저 검증. 실패 시 MS-05 를 "운영자 확인 후 구간 이동"으로 낮춘다 |
| 위험 | 계단 자율 통과는 연구 수준. Nav2 2D 지도는 계단을 다루지 않는다 | R3 첫 판은 계단 구간을 "운영자 확인 + 계단 보행 모드" 또는 수동 조종으로. [04 §5.3](04-ARCHITECTURE.md) |
| 위험 | 시뮬에서 STOP 뒤 3.6 s · 0.32 m 더 움직인 기록이 있다(원인 미확인) | 실기 전 원인 확인. STOP 은 "정지 보장"이 아니라고 화면·문서에 일관되게 적는다 |
| 제약 | 센서 구성(D435i, L1/L2, XT-16)은 제안이지 확정이 아니다 | 센서는 "부착 장치 목록"으로 받아 화면이 있는 것만 그린다 |
| 제약 | Go2 기종은 EDU 로 확정(10-19). 펌웨어·온보드 컴퓨터 사양은 미확인 | 로봇 에이전트는 EDU 온보드 컴퓨터에서 실행. 사양이 부족하면 소형 PC 추가를 검토 |
| 가정 | 현장망(Wi-Fi/LTE 사설망)에서 서버와 로봇이 연결된다 | 끊김은 정상 상황으로 설계 |

## 9. 미결 사항
| # | 질문 | 작성자 제안 |
|---|---|---|
| Q1 | 후진 허용? **결정(2026-10-25)** | 시뮬 시험용 후진(−0.3~−0.05 m/s)·옆걸음·제자리 회전 허용, 실기는 금지. 시뮬에서도 넘어질 수 있으며 보행·물리 정지를 보장하지 않는다([기존 조사](DRIVE-MODES-VALIDATION.md)) |
| Q2 | 임무·시나리오 "등록" 자체도 결재가 필요한가? | 아니오. 등록은 초안이라 로봇에 영향이 없다. 로봇에 영향이 생기는 **배정** 때 그 판을 결재한다 (결재 두 번을 피함) |
| Q3 | 총괄의 "강제 회수"(조종권자가 거절해도 가져오기) | 두지 않는다. 대신 STOP 은 누구나. 요청 창 무응답은 자동 거절(SF-06, 기존 조종 유지)이고, 조종권자 연결이 끊긴 경우에만 조종권이 비워진다(SF-08) |
| Q4 | 한 로봇의 담당 운영 관리자 수 | 1명. 대리 담당이 필요하면 P2 |
| Q5 | 자율 실행 중 서버 연결이 끊기면? | 끊긴 때(마지막 서버 신호 수신 시각, [04 §3.2](04-ARCHITECTURE.md#32-연결-끊김-처리))부터 `link_loss_wait_s`(조직 설정, 기본·상한 30 s) 안에 다음 지점에 닿으면 그 앞에서 대기, 시간이 먼저 지나면 그 자리에서 정지·잠금. 재연결 뒤 사람이 재개 |
| Q7 | deadman 만료(SF-03) 때 STOP 처럼 잠금까지 걸까? | 건다(제안). 기존 시험 기대값이 바뀌는 **새 안전 정책**이라 Core 이식이 끝난 뒤 별도 작업·별도 PR 로 하고, 두 모델 검토와 제품 책임자 승인을 받는다([08 §3](08-DEV-PROCESS.md#3-합치는-관문)) |
| Q6 | 제품 공식 이름 ("FOOTHOLD 관제 앱" / "현장 로봇 운영 앱") | 미정 |
