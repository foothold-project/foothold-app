## 2. 문서 규칙
- 요구사항 ID(`SF-01` 등)는 PRD 에서 정하고, 다른 문서는 그 ID 를 가리킨다.
- 상태 표기: **확정**(제품 책임자 결정) / **제안**(작성자 제안, 확인 필요) / **미확인**(사실 확인 전). 미확인은 결론에 쓰지 않는다.
- 문서를 고치면 문서 끝 "변경 이력"에 한 줄 추가하고 판을 올린다(0.1 → 0.2). 큰 방향이 바뀌면 ADR 을 새로 쓴다(ADR-002 …).
- 문서와 코드가 다르면: 타입은 서버 Pydantic 모델이 정본이고, 문서를 맞춘다. 동작·정책은 문서가 정본이고, 코드를 맞춘다.
- 진행 기록·검수 증거는 이 폴더에 넣지 않는다(각 작업 폴더 `runs/`).

## 3. 용어집

| 용어 | 뜻 | 코드 이름 |
|---|---|---|
| 총괄 운영 관리자 | 조직의 모든 로봇·계정·지도·임무를 맡는 사람. 결재권자 | `ORG_ADMIN` |
| 운영 관리자 | 자기에게 등록된 로봇을 맡는 사람 | `OPERATOR` |
| 담당 로봇 / 내 로봇 | 운영 관리자에게 배정된 로봇 | `robots.owner_user_id` |
| 관제 | 로봇들의 상태·위치·임무를 보는 화면 | Fleet |
| 조종권 | 한 로봇을 직접 조종할 수 있는 권리. 로봇마다 한 명 | lease |
| 조종권 요청 | 다른 사람이 조종 중일 때 넘겨 달라고 보내는 요청 | lease request |
| STOP | 0 명령 + 잠금. 몸이 즉시 멈춘다는 보장은 아님 | stop |
| 정지 잠금 | STOP 뒤 상태. 조종권자가 해제해야 움직임 | latched |
| deadman | 입력이 0.3 s 끊기면 로봇이 스스로 멈추는 장치 | — |
| 작업 | 한 지점에서 하는 한 동작(사진·대기·운영자 확인·센서 기록) | action |
| 임무 | 작업 묶음. 재사용 | mission |
| 시나리오 | 지도(여러 층 가능) 위 지점 순서 + 지점마다 임무 | scenario |
| 배정 | 시나리오 판을 로봇에 연결 | assignment |
| 실행 | 배정의 한 번 실행 기록 | run |
| 판 | 고칠 때마다 새로 생기는 번호 붙은 사본. 판은 바뀌지 않음 | version |
| 결재 | 운영 관리자의 지도 수정·시나리오 배정을 총괄이 승인/반려하는 절차 | approval |
| 긴급 실행 | 결재 없이 이유를 적고 바로 실행. 사후 확인 대상 | emergency run |
| 사후 확인 | 긴급 실행 뒤 총괄이 확인하는 결재 항목 | POST_REVIEW |
| 층 연결점 | 위아래 층을 잇는 계단(향후 엘리베이터) 양 끝 지점 짝 | floor connector |
| 실행 전 점검 | 실행 시작 전에 배터리·위치·연결 등을 확인하는 목록 | precheck |
| 경로 이탈 | 계획 경로에서 기준 거리 이상 벗어남 | route deviation |
| 관제 서버 | 인증·권한·결재·기록·중계를 하는 현장 서버 | server |
| 로봇 에이전트 | 로봇 쪽에서 안전 판단·임무 실행·송신을 하는 프로그램 | agent |

## 4. 폐기한 문서

2026-10-19 제품 책임자 결정("지금 만들어놓은 웹, 앱 기획 관련 문서들은 모두 파기하고 하나로 통일")에 따라 아래 문서는 **더 이상 기준이 아니다**. 진행 기록·검수 증거(PROGRESS·QA·CODEX 리뷰·serve 기록 등)는 이력으로 남긴다.
