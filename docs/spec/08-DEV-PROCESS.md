# 재구축 작업 방식 — Claude·Codex 분담과 진행 규칙

| 항목 | 내용 |
|---|---|
| 문서 번호 | FH-SPEC-08 |
| 판 | 0.1 |
| 작성일 | 2026-10-19 |
| 관련 | [07 ADR-001](07-ADR-001-REBUILD.md) · [Git 규칙](../GITHUB-WORKFLOW.md) · [AGENTS.md](../../AGENTS.md) |

[07 ADR-001](07-ADR-001-REBUILD.md)의 방식(새 골격 + 디자인·안전 로직 이식)으로 새 앱을 만드는 동안의 작업 규칙이다. Git 브랜치·PR·배포 규칙은 [GITHUB-WORKFLOW](../GITHUB-WORKFLOW.md)를 그대로 따르고, 이 문서는 **누가 무엇을 하고 어떤 관문을 지나야 합치는지**만 정한다.

## 1. 역할

| 역할 | 맡는 쪽 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| 조정 | Claude 조정 세션 1개 | 작업 나누기, 작업 지시서 작성, 작업자 배정(Orca), 검토 결과 판정, `dev` 합치기, 진행표 관리, 보고 | 앱 코드 직접 작성 |
| 구현 — 서버·로봇 쪽 | Codex 작업자 | `apps/server`, `apps/agent`, 계약(Pydantic → TS), DB 마이그레이션, 안전 Core 이식 | 화면 디자인 결정 |
| 구현 — 화면 쪽 | Claude 작업자 | `apps/web` 화면·디자인 이식·문구, 화면 단위 시험 | 서버 계약 임의 변경 |
| 코드 검토 | **만든 쪽과 다른 모델** | Codex 가 만든 것은 Claude 가, Claude 가 만든 것은 Codex 가 검토 | 검토하면서 코드 수정 |
| 화면 QA | Claude 작업자 | 고정 사본·별도 포트에서 사용자 흐름·누름 수·금지어 확인 | 운영 앱·실행 중 시뮬 접촉 |

- 서버와 화면 사이 약속은 **계약이 정본**이다. 계약을 바꾸는 작업은 서버 쪽이 먼저 PR 을 내고, 화면은 생성된 TS 타입을 쓴다.
- 한 작업은 작업자 한 명이 끝까지 한다. 검토 지적을 고치는 것도 같은 작업자가 한다.

## 2. 작업 하나의 흐름

```
조정: 작업 지시서 → 작업자 배정 (Orca, 작업마다 별도 worktree·브랜치)
구현: origin/dev 에서 feature/<작업명> → 구현·시험 → push → dev 대상 Draft PR → 완료 보고
검토: 다른 모델이 PR diff 검토 → 지적 목록 (막는 것 / 권고)
구현: 막는 지적 수정 → push
조정: 수용 기준 명령 재실행 확인 → dev 에 merge commit 으로 합침
```

### 2.1 작업 지시서 (조정이 작성)
모든 지시서에 다섯 가지를 쓴다.

| 항목 | 내용 |
|---|---|
| 대상 | 손댈 폴더·파일, 관련 요구사항 ID(`SF-01`, `F-TO-04` 등) |
| 결과 | 끝났을 때 무엇이 되어 있어야 하나 |
| 제약 | 지켜야 할 규칙, 건드리면 안 되는 곳 |
| 소유 | 이 작업자가 고칠 수 있는 경로 (다른 작업자와 겹치지 않게) |
| 수용 기준 | 통과해야 할 명령과 기대 결과 |

### 2.2 완료 보고 (작업자가 작성)
브랜치·커밋, PR 번호, 실행한 시험 명령과 결과, 바꾼 파일, 미검증 범위. «통과»는 실제로 돌린 명령 결과로만 쓴다.

### 2.3 검토 지적
- **막는 것**: 요구사항 위반, 안전·권한 결함, 시험 실패, 데이터 손실, 계약 불일치. 고치기 전에는 합치지 않는다.
- **권고**: 이름·구조·가독성. 작업자가 판단해 반영하거나 이유를 남긴다.
- 검토자는 지적만 하고 코드를 고치지 않는다.

## 3. 합치는 관문

| 대상 | 조건 | 누가 합치나 |
|---|---|---|
| 기능 → `dev` | 수용 기준 통과 + 다른 모델 검토의 막는 지적 0 | 조정 세션 |
| **안전 범위** → `dev` (STOP·deadman·잠금·조종권·명령 경로·인증·권한) | 위 조건 + Claude·Codex **두 모델 모두** 검토 + 기존 안전 셀프테스트를 고치지 않고 통과 | 조정 세션 |
| `dev` → `main` | [GITHUB-WORKFLOW §3](../GITHUB-WORKFLOW.md) | **제품 책임자 승인 후** |

- 안전 셀프테스트 기대값을 바꿔서 통과시키지 않는다. 바꿔야 한다면 별도 PR 로 이유를 적고 제품 책임자 승인을 받는다. 동작을 바꾸는 새 안전 정책(예: deadman 만료 때 잠금, PRD Q7)이 여기에 해당한다 — 이식 PR 과 섞지 않는다.
- 충돌 해소로 내용이 바뀌면 수용 기준을 다시 돌린다.

## 4. 동시 진행
- 동시에 도는 작업자는 **최대 3개**(보통 구현 2 + 검토 1).
- 작업마다 별도 worktree·브랜치. 같은 파일을 두 작업자가 동시에 소유하지 않는다.
- 서로 기다리는 작업은 순서를 정하고, 기다리지 않는 작업은 같은 차례에 함께 띄운다.

## 5. 새 코드 위치

| 폴더 | 내용 |
|---|---|
| `apps/web` | 새 웹 앱 (PC 6탭 + 폰 3탭) |
| `apps/server` | 관제 서버 (FastAPI, PostgreSQL, Alembic) |
| `apps/agent` | 로봇 에이전트 (안전 Core, 임무 실행기, ROS 2 다리) |
| `apps/contracts` | 계약 모델과 TS 생성 |

**이 재구축 작업의 작업자는** 기존 `ui/`, `server/`, `sim/`, `contracts/`, `mobile/` 을 **읽기만** 한다(이식할 때 복사 원본). 기존 앱 담당자의 유지보수·hotfix 는 [GITHUB-WORKFLOW](../GITHUB-WORKFLOW.md)와 각자의 지시서를 따른다. 새 앱으로 바꾼 뒤 별도 PR 로 정리한다.

## 6. 하지 않는 것

**제품 책임자 승인을 받은 뒤에만**
- 지금 운영 중인 앱·서버·포트, 실행 중인 시뮬(Gazebo)·ROS 도메인 접촉, 재시작.
- 로봇 명령 송신, 실기 Go2 연결.
- 새 시뮬 기동은 운영 시뮬과 다른 ROS 도메인·포트에서만, 처음 한 번은 승인 후.
- `main` 합치기, GitHub 저장소 설정 변경, 브랜치 삭제.

**승인과 관계없이 하지 않음**
- 공개 저장소에 계정·토큰·운영 주소·사진·지도 원본·빌드 산출물 커밋.
- 다른 세션의 worktree 조작(그 소유자나 조정 세션의 명시적 인계 없이).

## 7. 시험 기준
| 범위 | 최소 시험 |
|---|---|
| `apps/agent` 안전 Core | 이식한 기존 셀프테스트 전부 + 새 단위 시험 |
| `apps/server` | pytest (권한·조종권·결재·판 충돌 포함), 마이그레이션 왕복 |
| `apps/web` | 타입 검사, vitest, 빌드 |
| 계약 | 생성물이 커밋본과 같음 (재생성 diff 0) |
| 화면 흐름 | 화면 QA: 누름 수 목표([01 §6](01-PRD.md)), 금지어 0, STOP 상시 표시 |
