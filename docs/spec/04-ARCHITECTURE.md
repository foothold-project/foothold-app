## 1. 지금 구조 (2026-10-19, 코드 확인)

```
브라우저/폰 ──HTTPS·WS──▶ v2_gate (tornado, HTTPS, 로그인·권한)
                              │ X-FH-Actor 헤더
                              ▼
                         v2_link (로봇 1대당 1개, 127.0.0.1, 인증 없음, 안전 판단)
                              │ ROS 2 (<개발용 ROS_DOMAIN_ID>, LOCALHOST)
                              ▼
                         시뮬 Go2 (Gazebo + RL 보행 정책)
```
- 계정: `accounts.json` 파일(scrypt). 세션: 게이트 메모리(재시작하면 모두 로그아웃).
- 로봇 목록: `registry.json` 파일. 멀티로봇 게이트 코드는 작업 사본에만 있고 커밋·서비스되지 않았다.
- 근거 구분: 이 절은 별도 미커밋 작업 사본의 관측을 포함한다(이 저장소 HEAD 의 `sim/v2_gate.py` 에는 멀티로봇 라우트가 없고, 게이트 인증 모듈은 저장소 밖 원본을 읽는다). 이 PR 로 재현되지 않는 내용은 참고로 보고, 외부 게이트·인증 원본 확보를 R0 선행 조건으로 둔다.
- 데이터: v2_link 마다 따로(docs.json 또는 SQLite, events.jsonl, 사진 폴더). 로봇을 가로지르는 공용 DB 없음.
- 조종권: v2_link 안에서 연결 ID 하나. 먼저 잡은 사람이 갖고, 넘기기 규칙 없음.
- 실기 Go2: 어댑터는 오프라인 준비판(mock 만). 실기 연결 0.

문제: ① 로봇마다 데이터가 흩어져 조직 단위 관제가 안 된다 ② 사람 신원이 헤더 문자열이다 ③ 로봇이 서버와 같은 PC 에 있어야 한다(127.0.0.1) ④ 결재·감사 기록을 둘 곳이 없다.

### 2.1 구성 요소

|---|---|---|---|
| 웹 앱 (PC·폰 공용) | 화면. 폰은 같은 앱의 폰 틀 | React + TypeScript + Vite (지금과 같음), PWA | 디자인 토큰·CSS, 순수 로직 모듈 ([07](07-ADR-001-REBUILD.md)) |
| 관제 서버 | 인증·권한, 로봇 목록, 조종권 중재, 결재, 임무·시나리오, 사건 기록, 실시간 중계 | Python FastAPI + uvicorn, WebSocket | v2_gate 의 인증 방식(scrypt·쿠키·WS 티켓·속도 제한·권한 재확인), contracts/v1 (Pydantic → TS 생성) |
| DB | 조직·사람·로봇·지도 판·시나리오·결재·사건 | PostgreSQL 16 | store.py 의 판 충돌(rev·409) 규칙 |
| 파일 저장소 | 지도 이미지(pgm/png + yaml), 사진, 실행 보고서 | 서버 로컬 디스크 (경로 + sha256 을 DB 에) | 사진 저장 방식 |
| 로봇 에이전트 | 로봇 쪽 안전 판단, 조종 명령 적용, 임무 실행, 원격측정·영상 송신, 지도 보관 | Python (rclpy) 1 프로세스 + ROS 2 노드들 | **v2_link 의 안전 Core(deadman·잠금·중립 확인·명령 단계화)와 셀프테스트** |
| 로봇 내부 | 보행·이동·센서 | ROS 2 Jazzy, Nav2, SLAM Toolbox(제안), Unitree SDK2 | go2_adapter 의 Move/StopMove 규칙 |

### 2.2 왜 이 모양인가
| 결정 | 이유 | 버린 대안 |
|---|---|---|
| 로봇이 서버로 **먼저 접속**(outbound WSS) | 현장망·LTE·NAT 뒤에서도 연결됨. 서버가 로봇 IP 를 몰라도 됨 | 서버가 로봇에 접속(로봇 포트 열어야 함) |
| ROS 2 는 **로봇 안에만** | DDS 는 넓은 망에서 불안정하고 보안이 약하다. 기존 결정("rosbridge 포트 밖으로 안 엶")과 같음 | rosbridge 를 화면에 직접 연결, Zenoh 로 ROS 전체를 서버까지 다리 |
| 안전 판단은 **로봇 에이전트** | 서버·망이 죽어도 로봇이 스스로 멈춰야 한다 | 서버에서만 판단(지금 v2_link 방식은 서버=로봇 PC 라서 가능했음) |
| 임무 실행기도 **로봇 에이전트** | 실행 중 잠깐 끊겨도 현재 구간은 이어감, 사건은 쌓았다가 올림 | 서버가 지점마다 명령(끊기면 멈춤) |
| 서버 하나 + PostgreSQL | 사용자 20명·로봇 10대 규모에 충분. 결재·감사·동시 쓰기에 안전 | 로봇마다 SQLite(지금 구조, 조직 단위 조회 불가), Redis 등 추가 저장소(필요 없음) |
| 현장 로컬 서버 기본 | 인터넷 없는 현장에서도 동작 (기존 결정 D-4) | 클라우드 필수 |

Zenoh(zenoh-bridge-ros2dds) 는 **개발자 진단용**(로봇 토픽을 개발 PC 에서 보기)으로만 쓴다. 운영 화면 경로에는 넣지 않는다. 다중 로봇에서 TF 가 끊기는 알려진 문제도 있다.

## 3. 통신 경로

| 경로 | 프로토콜 | 내용 | 빈도 |
|---|---|---|---|
| 화면 ↔ 서버 | HTTPS REST | 목록·편집·결재·기록 조회 | 요청 때 |
| 화면 ↔ 서버 | WSS `/ws` | 구독한 로봇 상태, 사건, 알림, 조종 명령, 조종권 요청 | 상태 10 Hz, 조종 20 Hz |
| 서버 ↔ 로봇 에이전트 | WSS `/agent/ws` | 원격측정, 사건, 명령 전달, 임무 내려보내기, 지도 판 내려보내기 | 상태 10 Hz, 명령 20 Hz |
| 영상 1단계 | 위 WSS 위 JPEG 바이너리 | RGB 640×480 이하 10 Hz, 뎁스 색입힘 5 Hz, 라이다 점 5 Hz(내려 뽑은 이진 배열) | 보는 사람이 있을 때만 |
| 영상 2단계 | WebRTC (서버가 연결 중개, 현장망에서는 직접 연결) | RGB 고화질, 여러 명 동시 시청 | 1단계로 지연·대역이 부족할 때 |

- 영상은 **보는 사람이 있을 때만** 보낸다(서버가 구독 수를 세서 에이전트에 켜기/끄기).
- WebRTC 는 측정 결과 카메라 쪽 지연이 대부분이고 WebRTC 자체는 약 10 ms 를 더한다는 보고가 있다(전체 150~180 ms). 1단계에서 지연을 재고 나서 넘어간다.

### 3.1 조종 명령 경로 (3중 확인)
```
화면 ──cmd{robot, lease_id, seq, axes}──▶ 서버
       서버: ① 로그인·권한 ② lease_id 가 지금 조종권자인지 ③ 속도 제한
       ──cmd{lease_id, seq, axes, t_server}──▶ 로봇 에이전트
       에이전트: ④ lease_id 가 서버가 알려 준 현재 조종권인지 ⑤ seq 증가 ⑥ 0.3 s 안에 왔는지
                ⑦ 잠금·중립 확인 ⑧ 명령 단계화·속도 한계 ⑨ 장애물 감시(collision monitor)
       ──▶ Go2 (Move / StopMove)
```
- 어느 한 단계라도 실패하면 0 명령. 실패 이유는 사건으로 남기되 화면에는 짧게.
- STOP 은 이 경로와 별도로 우선 처리한다(권한: 그 로봇을 볼 수 있으면). 에이전트는 STOP 을 받으면 조종권과 상관없이 잠근다.
- 실기 Go2 의 무선 리모컨 비상정지는 이 소프트웨어와 무관하게 항상 살아 있어야 한다.

### 3.2 연결 끊김 처리
| 끊긴 곳 | 로봇 에이전트 동작 | 서버 동작 | 화면 |
|---|---|---|---|
| 화면 ↔ 서버 (조종 중) | 명령이 0.3 s 안 오면 0 명령 + 입력 폐기(deadman) | 마지막 유효 heartbeat 15 s 뒤 조종권 비움, 사건 | 띠 "연결 끊김" (로봇 상태는 마지막 확인 값) |
| 서버 ↔ 로봇 (조종 중) | 0.3 s 뒤 0 명령 + 입력 폐기(deadman) | 로봇 "끊김" 표시, 사건 | 띠 "Go2-3 연결 끊김 · 마지막 확인 …" |
| 서버 ↔ 로봇 (자율 실행 중) | 연결 유예 시작(아래). 사건은 쌓아 둠 | 재연결 시 쌓인 사건 받기 | 실행 "연결 끊김 · 마지막 확인 …" |
| 재연결 | 서버에 현재 상태 전부 보냄. 잠금은 풀지 않음. 유예 대기 중이었으면 대기 유지 | 조종권은 비운 상태 유지 | 사람이 다시 시작 |

**감시 장치는 모드별로 따로** (deadman 잠금 여부는 PRD Q7 이 정해질 때까지 현재 동작대로)
| 감시 | 언제 적용 | 기준 | 끝나면 |
|---|---|---|---|
| 수동 입력 감시 (deadman) | 사람이 조종권을 가짐 | 마지막 서버 `cmd` 수신 0.3 s | 0 명령 + 입력 폐기, 새 중립 필요 |
| 자율 명령 감시 | 실행이 조종권을 가짐(`RUN`) | 에이전트 안 임무 실행기가 마지막으로 낸 명령 0.3 s (서버 `cmd` 는 보지 않음) | 0 명령 + 실행 `FAILED`(실행기 멈춤) |
| 서버 연결 유예 | 실행이 조종권을 가진 채 서버 연결이 끊김 | 마지막 서버 메시지 수신 시각부터 `link_loss_wait_s`(기본 30 s, 0~60) | 그 안에 다음 지점에 닿으면 그 앞에서 대기(이 경우 대기가 먼저). 시간이 먼저 끝나면 그 자리에서 정지·잠금 |
- 사람이 조종 중일 때 서버 연결이 끊기면 서버 `cmd` 가 안 오므로 수동 입력 감시로 0.3 s 안에 0 명령이 된다. 유예는 자율 실행에만 있다.

## 4. 운영자 사이 간섭 막기

### 4.1 조종권 (lease)
- 로봇마다 조종권 하나. 서버의 **조종권 중재기**가 정본이고, 바뀔 때마다 로봇 에이전트에 `lease_id` 를 알려 준다.
- 상태: `FREE → HELD(사람, 기기, lease_id) → (요청 PENDING) → HELD(다른 사람)`.
- 조종권은 사람 + 기기 + 연결에 묶인다. 같은 사람이 PC 와 폰에서 동시에 잡을 수 없다(다른 기기로 옮기려면 끝내고 다시 잡기).
- heartbeat: 화면은 조종 중 50 ms 마다 명령(0 포함)을 보낸다. 서버는 15 s 동안 아무것도 못 받으면 조종권을 비운다(로봇은 이미 0.3 s 에 0 명령).
- 요청·넘기기 규칙은 [02 F-TO-04](02-FUNCTIONAL-SPEC.md#f-to-04-조종권-요청-sf-05sf-08--확정--제안-보완).

### 4.2 자율 실행과 수동 조종
- 실행 중에는 조종권 주인이 `RUN:<run_id>` 다. 사람이 조종을 시작하면 실행을 `PAUSED` 로 바꾸고 조종권을 사람에게 준다. 다시 실행을 재개하면 조종권은 `RUN` 으로 돌아간다(사람은 조종 끝내기).
- 같은 로봇에 실행은 동시에 하나(DB 부분 고유 인덱스, 지금 SQLite 의 `one_active_run` 과 같은 방식).

### 4.3 편집 충돌
- 임무·시나리오·지도 편집은 판 번호로 충돌을 막는다(낙관적 잠금): 저장할 때 "내가 고친 기준 판"을 같이 보내고, 그사이 다른 판이 생겼으면 409.
- 결재 승인 때도 같은 검사: 요청의 기준 판이 지금 승인 판과 다르면 `STALE`.

### 4.4 같은 일을 두 사람이 동시에
| 상황 | 처리 |
|---|---|
| 두 사람이 같은 로봇에 실행 시작 | 먼저 도착한 요청만 성공, 나머지 409 "이미 실행 중" |
| 두 총괄이 같은 결재를 동시에 처리 | 먼저 처리한 쪽만 성공, 나머지 "이미 처리됨" |
| 같은 사람이 여러 탭에서 접속 | 허용. 조종권은 하나의 탭(연결)에만 |

## 5. 로봇 사이 간섭과 층

### 5.1 로봇 식별
- 로봇마다 `robot_id`(UUID)와 에이전트 인증 정보(등록 때 발급하는 토큰, 2단계에서 기기 인증서). 서버는 연결 1개만 허용(같은 ID 로 두 번째 접속이 오면 앞 연결을 끊고 사건).
- 로봇 안 ROS 는 로봇마다 따로라 이름이 겹쳐도 상관없다. 시뮬에서 여러 대를 한 PC 에 띄울 때만 ROS 네임스페이스(`/go2_3/...`) 또는 DOMAIN ID 를 나눈다.

### 5.2 지도 공유
- 지도는 조직 공용. 승인 판만 로봇에 내려간다. 에이전트는 받은 판을 로컬에 보관(sha256 확인)해서 서버가 끊겨도 쓴다.
- 실행 중 지도 판은 고정(MP-04).

### 5.3 층 이동 (확정 요구, 단계 제안)
**데이터**: 층마다 2D 지도 1개. 층 연결점 = (층 A 지점, 층 B 지점, 종류: 계단).

**경로 계산 (서버)**: 층을 꼭짓점, 연결점을 변으로 하는 작은 그래프에서 현재 층 → 목표 층 경로를 찾는다. 층 안 경로는 로봇 에이전트의 Nav2 가 실행 때 계산한다.

**실행 (로봇 에이전트)**:
1. 현재 층 지도에서 연결점 A 까지 Nav2 목표 이동.
2. 층 전환 구간:
   - 첫 판: 운영자 확인 요청("계단 구간") → 수동 조종 또는 계단 보행 모드로 통과 → 운영자가 "n층 도착" 확인.
   - 다음 판: 정책이 지원하면 계단 보행 자동.
3. Nav2 지도 바꾸기: map_server `load_map`(또는 Nav2 Simple Commander `changeMap()`)으로 목표 층 지도를 올린다.
4. 위치 잡기: 연결점 B 의 알려진 위치를 초기 위치로 넣고(AMCL initial pose 또는 SLAM Toolbox localization), 확신도가 기준 이상인지 확인. 낮으면 운영자에게 묻는다.
5. 시작 지점까지 Nav2 목표 이동.

**현재 층 알기**: 기본은 사람이 입력한다(실행 전 점검, 층 전환 확인). 로봇은 마지막으로 확인된 층을 기억한다. 자동 판별은 후속 과제다.

**확인 필요(미확인)**: Go2 계단 자율 보행이 이 프로젝트의 보행 정책·실기에서 가능한지, 계단 치수, 엘리베이터 연동 여부.

### 5.4 같은 공간의 여러 로봇
- 첫 판: 교통 관리 없음. 같은 층에서 두 로봇의 계획 경로가 1 m 안으로 겹치면 실행 전 점검에서 **경고**만 한다.
- Nav2 장애물 회피는 서로를 장애물로 본다(라이다).
- 다음 판 후보: Open-RMF 교통 관리. 로봇이 많아질 때 검토.

## 7. 보안
| 항목 | 방법 |
|---|---|
| 전송 | 모든 경로 TLS (현장 사설 CA 가능, 지금 `/ca.crt` 배포 방식 유지) |
| 사용자 인증 | 비밀번호 scrypt. 웹: HttpOnly·Secure·SameSite=Strict 쿠키. 설치형 앱: 짧은 수명 bearer + WS 1회용 티켓(지금 방식 유지) |
| 로봇 인증 | 등록 때 1회 발급 토큰(서버는 해시만 저장), 2단계에서 기기 인증서(mTLS) |
| 권한 | 서버가 매 요청·매 WS 메시지·주기적(2 s)으로 다시 확인(지금 게이트 방식 유지) |
| 로그인 보호 | IP·계정당 실패 5회/5분 제한 |
| 기록 | 로그인·권한 변경·결재·조종권·STOP 모두 사건으로 |
| 노출 | 서버만 현장망에 공개. 로봇 ROS·에이전트 내부 포트는 열지 않음 |

## 8. 배포
- 현장 서버 1대(리눅스 PC): 관제 서버 + PostgreSQL + 파일 저장소. Docker Compose 로 묶는다(제안).
- 로봇마다 에이전트 1개(systemd 서비스).
- 시뮬: 개발 PC 에서 시뮬 Go2 여러 대 + 에이전트 여러 개(네임스페이스로 나눔). 지금 Gazebo 시뮬은 에이전트 하나 뒤에 붙인다.
- 백업: `pg_dump` 매일 + 파일 저장소 매일 복사.
- 시간 동기화: 서버·로봇 모두 chrony(NTP). 사건 시각은 서버 기준으로 정렬하되 로봇 시각도 같이 저장.
