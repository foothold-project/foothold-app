# GitHub 개발·검증·배포 규칙

적용일: 2026-10-19. 사용자가 요청한 `main` / `dev` 구조를 이 저장소의 기준으로 삼는다. 이 문서는 이전 2026-10-14 작업 방식의 브랜치·PR 기준을 대체한다. 저장소는 공개이며 다른 저장소·팀 inbox·학습 작업에는 적용하지 않는다.

## 1. 브랜치의 역할

| 브랜치 | 역할 | 반영 방법 |
|---|---|---|
| `main` | 검증된 배포 기준 코드 | 원칙적으로 `dev` → `main` PR |
| `dev` | 다음 버전의 웹·서버·모바일 통합 및 검증 | 기능별 작업 → `dev` PR |
| `feature/<작업명>` | 개별 기능 개발 | `dev`에서 시작, 검토 후 `dev`로 PR |
| `fix/<작업명>` | 일반 오류 수정 | `dev`에서 시작, 검토 후 `dev`로 PR |
| `hotfix/<작업명>` | 현재 배포판의 긴급 수정 | `main`에서 시작, 검증 후 `main`으로 PR, 이후 `dev`에도 반영 |

`dev`는 `main`의 하위 폴더가 아니다. 독립 브랜치이며 변경을 합치는 순서가 정해져 있다. 최초 구성에서는 두 브랜치가 같은 커밋에서 시작한다.

진행 중인 `less82/app-ui-react-recovered`, `less82/app-contract-storage`, `less82/app-platform-integration`은 보존한다. 강제 이름 변경이나 작업 폴더 재설정 없이 담당 작업을 이어가며, 앞으로 검토할 변경의 통합 목적지는 `dev`다. 기존 통합 브랜치는 전환 기간의 조립 작업용이며 별도의 영구 배포 기준으로 삼지 않는다.

## 2. 개발과 통합

1. 변경 전 `git status --short --branch`로 자신의 경로와 브랜치, 미커밋 파일을 확인한다. 동시에 같은 브랜치를 여러 폴더에서 편집하지 않는다.
2. 새 작업은 최신 `origin/dev`를 기준으로 별도 브랜치에서 시작한다. 기존 담당 브랜치는 미완료 작업을 보존한 상태에서 필요한 기준 변경만 검토하여 가져온다.
3. 의미 있는 변경 단위로 커밋한다. 검증 전 커밋도 기능 브랜치에는 보관할 수 있지만 «미검증»임을 적고 배포 완료로 표시하지 않는다.
4. 기능 PR의 base는 `dev`다. 변경한 기능, 영향, 검증 결과, 남은 한계를 적는다. 검토 전에는 Draft PR을 사용할 수 있다.
5. `dev`에 통합한 정확한 후보 커밋을 대상으로 필요한 통합 검증을 수행한다. 기능 브랜치에서만 통과한 결과를 통합 결과로 대신하지 않는다.
6. 검증 뒤 코드가 바뀌면 바뀐 영향에 맞게 재검증한다. 실패한 검사나 미확인 사항을 삭제하거나 PASS로 바꾸지 않는다.

웹·서버와 모바일을 합칠 때는 최신 웹·서버 기준 위에 검토된 `mobile/**`를 반영한다. 오래된 모바일 브랜치 전체를 무조건 merge하여 `ui/`, `server/`, `sim/`, `contracts/`를 되돌리지 않는다. 필요한 선택 반영과 출처 커밋·트리 해시를 [통합 출처](PROVENANCE-app-platform-integration.md)에 기록한다.

## 3. main에 반영하는 조건

- 보통 `dev` → `main` PR 하나로 올린다. 문서·검증 기록만으로 최초 기준을 구성한 2026-10-19 부트스트랩은 한 번의 예외다.
- PR에는 **검증한 커밋과 실제 반영 후보 커밋**, 검사 명령·결과, 실행 환경, 알려진 한계, 배포 영향, 되돌림 방법을 적는다.
- 변경에 해당하는 타입·단위·계약·서버·화면·모바일 검사가 통과해야 한다. 로봇 명령·STOP·인증·권한·연결 전환 변경은 해당 경계의 회귀 검증도 포함한다. 모든 변경에 모든 종류의 시험을 강요하지 않는다.
- 새로 도입한 배포 차단 결함이 없어야 한다. 범위 밖의 기존 미구현 기능은 명시하며, 배포판의 실제 지원 범위를 넘겨 완료라고 쓰지 않는다.
- UI·서버·모바일 조합과 검사 대상이 맞아야 한다. APK가 서버를 포함한다고 가정하지 않는다.
- 검토 기록을 남기고 일반 merge commit으로 이력을 보존하는 방식을 기본으로 한다. 배포 후보를 바꾸는 충돌 해소가 있었다면 그 결과를 다시 검사한다.
- 기능 개발을 `main`에서 직접 하지 않는다. `main`과 `dev`에 force push·이력 삭제를 하지 않는다.
- `main` 반영 후 필요한 merge 기록과 hotfix를 `dev`에도 가져와 분기를 정리한다. 이미 반영된 기능을 중복 구현하지 않는다.

`main`은 기록된 범위의 배포 기준이다. «모든 기능 완성», «실폰 확인 완료», «실로봇 안전 보장»이라는 뜻이 아니다.

## 4. 검증과 배포는 구분

| 기록 | 뜻 |
|---|---|
| 소스·정적 검사 | 코드·타입·스키마 등 명시한 검사 범위 |
| 단위·모의 검증 | 시험 코드와 가짜 응답에서 관측한 범위 |
| 빌드·APK 구조 대조 | 산출물 생성과 파일·버전·서명 등의 대조, 실행 통과 아님 |
| 에뮬레이터 실행 | 명시한 에뮬레이터에서 앱 실행, 실폰 아님 |
| 실폰 실행 | 기종·OS·앱 버전을 적은 실제 휴대폰 시험 |
| 실로봇 검증 | 실제 기체·펌웨어·연결 방식에서 명시한 시험 |

- GitHub에 push하거나 `main`에 merge한다고 서비스가 자동으로 배포되는 것은 아니다. 배포 자동화를 별도로 설정한 경우에만 해당 설정이 실행된다.
- 운영 웹 교체는 대상 커밋·빌드·서버 호환·보관 자료·되돌림을 확인하는 기존 절차를 따른다. Git 구조 전환만으로 서버를 재시작하지 않는다.
- `dev` 빌드는 개발·시험용이다. 정식 배포와 구분한다.
- 설치된 앱은 push만으로 바뀌지 않는다. APK에는 화면 번들이 들어가므로 새 APK 설치가 필요하다. 서버 변경은 기존 APK와의 호환도 확인한다.
- APK마다 `versionCode`를 증가시키고 같은 앱 ID·서명 계보를 유지한다. 이미 배포한 APK·태그·체크섬은 덮거나 삭제하지 않는다. 공개 원물에는 버전·소스 커밋·체크섬·검증 범위를 함께 적는다.
- 개발판은 prerelease로 구분한다. 태그 하나는 정확한 통합 커밋과 산출물을 가리켜야 한다. 빌드 산출물은 Git 소스 이력에 넣지 않는다.
- IPA는 실제 빌드·서명·배포 검증 전에는 제공된다고 쓰지 않는다.

## 5. 공개 저장소에 올리지 않는 것

- 계정·비밀번호·세션·토큰·개인키·서명 키·운영 `.gate/`·비밀 환경 파일.
- 실제 운영 주소·개인 경로를 새 문서에 넣지 않는다. 예제는 익명화한 값과 저장소 상대 경로를 쓴다. 기존 자료의 경로가 남아 있다고 새 자료에도 복사하지 않는다.
- `runs/`, `reference/`, 사진·영상·지도·점군 원본, 로컬 보고서 `output/`, 임시 파일 `tmp/`.
- `node_modules/`, 가상환경, `dist/`, `www/`, `out/`, `build/`, APK·AAB·IPA, `local.properties`.

`git add .` 대신 제출 경로를 지정하고 staged diff와 공개 범위를 확인한다. 커밋 작성자 이메일은 GitHub noreply를 쓴다. 기존 비공개 자료와 미커밋 파일은 브랜치 정리 때문에 삭제하지 않는다.

## 6. 되돌리기

- 코드 문제는 `git revert`로 새 수정 커밋을 만든다. `main` 이력을 강제로 되돌리거나 덮어쓰지 않는다.
- 운영 중인 빌드 되돌림은 기존 배포 절차와 보존 원물을 사용한다. Git revert 자체가 운영 교체는 아니다.
- APK는 이전 안정 소스로 새로 빌드하되 더 높은 `versionCode`로 배포한다. 사용자에게 앱 삭제를 기본 복구 방법으로 안내하지 않는다.
- 복구 내용을 `dev`에도 반영한다.

## 7. GitHub 관리자 설정과 전환 상태

2026-10-19 확인 결과, 작업 계정은 저장소 **쓰기 권한만 있고 관리자·maintain 권한은 없다**. 따라서 아래는 규칙 문서이며 GitHub에서 강제로 적용됐다는 뜻이 아니다.

관리자가 마무리할 설정:

1. 기본 브랜치를 `feature/two-device`에서 `main`으로 변경한다. `dev`를 대상으로 하는 기능 PR은 base를 명시한다.
2. `main`과 `dev`의 ruleset 또는 branch protection에 PR 필수, force push·브랜치 삭제 금지, 대화 해결과 실제 사용하는 필수 검사를 설정한다. 검토 인원은 실제 협업 인원에 맞춰 정한다.
3. 검사 이름은 실제 workflow에서 성공한 체크를 확인하고 등록한다. 존재하지 않는 검사를 필수로 만들어 모든 PR을 막지 않는다.
4. 기존 PR #1·#2는 이전 기준과 오래된 head를 갖고 있다. 작성자가 최신 후보와 base를 확인하여 후속 PR로 대체하거나 정리한다. 과거 PR을 바로 merge하여 새 `main`을 덮지 않는다.
5. 배포 자동화를 연결할 때 운영은 `main`, 미리보기·시험은 `dev`로 지정한다. 기존 도메인·서버·위키·APK 공개 설정은 별도 작업이다.

이 전환은 기존 브랜치·태그·PR·배포 원물을 삭제하지 않는다. 현재 작업 폴더의 브랜치를 바꾸는 것은 별도이며, GitHub 기본 브랜치 변경과도 다르다.

## 8. 최초 기준
